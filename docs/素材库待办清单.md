      `scanMissing()` 的返回从 `{missing, restored, scanned}` 扩到带 `remaining`（**扫完仍然缺**的条数，
      不是扫之前那条快照，否则边扫边恢复会把按钮数字算错）；`PhotoRepository.listMissingIds()` 只回 id
      （走既有的 `listMissing()` 会把 5,001 条 `filePath` 整列传过 IPC，纯浪费）；
      `moveMissingToTrash()` 复用 `deletePhotos()` 那道软删，所以**回收站照常能还原**、磁盘上一个字节都不删。

      活的素材绝不会被连带：`listMissingIds()` 的 SQL 同时要求 `deleted_at IS NULL AND missing_at IS NOT NULL`，
      回收站里本来就在的丢失行也不进第二次清单。
- 验收 `e2e/missing-triage.spec.mjs`：造 1 条断链 + 1 条健康，`scanMissing().remaining` 必须是 1，
      点批量后 `removed` 是 1、活素材仍在列表、**活素材的库内副本还在盘上**（清空回收站后再查一次哨兵，
      防的是"批量误删无主文件"那条链），最后 `remaining` 归 0。
- [x] **右键「复制文件夹路径」改给出处目录**（细节见上面三十轮·审查后那条）。
- [x] **`wallpaper-ui.probe` 那条时好时坏的断言**：根因不在壁纸，在探针——`UToastProvider` 的
      DOM 里没有 `role`、类名也不含 "toast"，唯一能命中 `[class*="toast"]` 的是 240ms 的

      说明红的是探针不是功能。

      链路：入库处理音频分支一次 `ffmpeg` 解码（单声道 4 kHz PCM）→ 400 桶峰值 + 节拍估计
      → 迁移 024 的 `waveform BLOB / bpm REAL` → `audio:waveform` 按 id 取（400 B 一条，

      （原来按空格是把预览关掉，和"点了没反应"叠在一起就像音频放不了）。
      节拍算法：半波整流能量差分 → 按参与项数归一的自相关 → 4 次谐波加权求和 →
      0.25 帧小数滞后线性插值 → 120 附近的对数正态先验 → 折进 [70,180)。
