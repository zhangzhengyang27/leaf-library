## 三、根因

1. **没有版本控制 = 没有底稿**。三周高强度开发期间 git 一次都没提交；出事时能靠的只有一次恰好留下的构建产物。
2. **单点存储**。源码、库数据、构建产物全在一块盘的同一条桌面目录树里，没有第二副本、没有远端。
3. **多会话并行写同一工作区，无任何约定**。第二击的直接根因；两个会话都「以为盘上是自己上次看到的样子」。
4. **文档与配置同属无备份资产**。事故连 .gitignore 一起带走，恢复件本身成了新的风险面。

## 五、教训（制度化后的表述）

1. **没进版本库的代码等于不存在**。每天至少一次提交；仓库必须有远端。
2. **单测全绿 ≠ 功能在**。绿灯塔照不到的链路靠真跑 e2e；`continue-on-error` 的门禁等于没有门禁。
3. **并行写盘必须互斥**。见 `AGENTS.md` 写盘纪律——同一时刻只允许一个会话写工作区。
4. **评测判据不进仓就会被 /tmp 吃掉**。AI 评测图池随 /tmp 丢失过一次，fixture 进仓从此是规矩。
   连**应用图标**都曾以 /tmp 符号链接的形式「入仓」——`resources/icon.png` → `/tmp/leaf-tmp-icon.png`，
   /tmp 一清构建链即断（2026-09-25 打包验证时才发现，从 out/ 构建产物里找回 512×512 原字节换成真文件）。
5. **恢复产物要及时归档出源码树**。`*.bundle.ts` 与真实源码同名相邻是误 import 与检索污染的持续来源。
