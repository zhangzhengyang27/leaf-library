# 素材格式扩展：能力实测与分级方案

> 日期 2026-09-19。方法：**本机实测优先**——sharp 0.35.4 + libvips 8.18.6 二进制构建配置、真文件/合成文件解码矩阵、Electron 38.5.0（=Chromium 140.0.7339.249，Node 22.20.0）编解码探针、`qlmanage` 无头出图实测；生态库结论逐条对 npm registry + 上游仓库核实。对照基准：Eagle 官方格式清单（Win 106 / macOS 115）。
> 标注约定：**[实测]** 本会话跑过；**[核实]** registry/上游文档；**[未验]** 资料指向但本机没跑通，落码前需补探针。

## 一、真实解码能力边界

先记一个坑：**`sharp.format[k].input` 是对象 `{file,buffer,stream}` 不是布尔值**。用 `!!f.input` 判断会恒为 true，把 `jxl/rad/dcraw/magick/pdf` 全报成"支持"。能力判定只能读 `.input.file` 或真解码一次。

随包 libvips 8.18.6 的构建配置（从 dylib 里 `strings` 出来的原话）[实测]：

```
Magick load/save with MagickCore: false (dynamic module: false)
EXR load with OpenEXR: false      RAW load with libraw: false
JPEG2000 load/save with OpenJPEG: false      enable RAD load/save: false
UHDR load/save with libuhdr: true            (Ultra-HDR 增益图 JPEG 可读)
```

`.input.file` 为真的只有：`jpeg(.jpg .jpeg .jpe .jfif) png webp tiff gif svg heif(仅 .avif) vips`。

同一批文件在五个通道上的结果 [实测]：

| 输入 | sharp | 自带 ffmpeg 4.4 | Chromium 140 | nativeImage | `qlmanage -t` |
| --- | --- | --- | --- | --- | --- |
| exr / tga / dpx / sgi / jp2 | 拒 | **→ PNG 成功** | 拒 | 拒 | — |
| hdr（Radiance，真文件） | 拒 | 拒（4.4 无解码器，6.0 线才加 [核实]） | 拒 | 拒 | **→ PNG 成功** 126 KB |
| heic（sips 造） | 拒（libheif 缺 libde265） | — | `<img>` **拒** | 拒 | — |
| avif | **编解都通** | — | `<img>` **通** | 拒 | — |
| xlsx | — | — | — | — | **→ PNG 成功** |
| obj | — | — | — | — | 无产出（系统无 QL generator） |
| eps | — | — | — | — | 30 s 无产出 [核实=agent 实测] |

视频容器在 `<video>` 里 [实测，用自带 ffmpeg 造样]：**能播** = h264.mp4、**hevc.mp4(hvc1)**、**av1.mp4**、vp9.webm、**h264.mkv**、3gp；**不能播** = **prores.mov**、**h264.ts(MPEG-TS)**、flv、wmv。

结论：**sharp 只负责主流位图；自带 ffmpeg 是唯一已到位的通用光栅器；Chromium 负责 avif/多容器视频但不含 heic 与 prores；nativeImage 只认 png（不是 ImageIO 桥）**。

## 三、分层策略：四条轴 × 四档解码

一个格式"支持"到什么程度是四个独立问题，Eagle 的天花板在第 4 轴（它只有文件名可搜）：

- **A 归类入库**：扩展名 → `kind`（改 `src/shared/assetTypes.ts` 一处）
- **B 代表图**：解码档链 T1 sharp → T2 专用解析（PSD 资源块 / Sketch `previews/` / OOXML / 3D 出帧）→ T3 自带 ffmpeg → T4 OS 兜底（可选）→ 字母卡
- **C 全量预览**：Chromium 原生 → pdfjs → 自研渲染器（three / 字体标本 / 波形）→ **代理转码**（ProRes/TS/FLV/WMV 必须转 H.264）
- **D 可检索**：文本抽取进 FTS（已有 `photo_fts`，含 `ocr_text`）——这条是差异化，且大量复用现成件

## 七·C、HEIC 跨平台解码档（2026-09-19 同日，第二批）

`heic-decode@2.1.0`（ISC，16K）+ 传递依赖 `libheif-js`（LGPL-3.0，6.1 MB，wasm-bundle 变体——wasm 内嵌在 JS 里，因此不需要 asarUnpack）。接在 `imageConvert.ts:convertHeicToPng` 的 sips 之后作为第二级，Windows 由此从"完全无解码路径"变成能出封面。

三条实测结论（都是踩出来的，不是文档读的）：

1. **`libheif-js` 必须锁 1.19.8**。heic-decode 声明 `^1.19.8`，pnpm 默认解析到 1.23.2 后直接抛 `Spread syntax requires ...iterable[Symbol.iterator] to be a function`；A/B 两版跑同一个真 HEIC，1.19.8 解出 64×48 RGBA。已用 `pnpm.overrides` 钉住（做成直接依赖会掩盖"为什么要锁它"）。
2. **解码输出是正向行序，不要 flip**。用一个上红下蓝的 HEIC 夹具按坐标取像素验的（`h_asis` y0=红 / y47=蓝，`h_flip` 反之）。第一版探针取 x=0 与 x=32 都落在 testsrc 的黑边/均匀区，判不出方向——判方向必须用纵向不对称的夹具。
3. **`img.data` 不能直接喂 `img.data.buffer`**：那是整块 wasm 堆，必须 `Buffer.from(img.data)` 按视图拷贝。

`.hif` 同轮补进 `IMAGE_EXTENSIONS` + `isHeicPath`（Eagle 格式表里有它，我们之前缺）。补完 30 秒内被守卫用例逮了一次——它报 `expected ['hif'] to deeply equal []`，因为 `formatCapability` 的通道表里没有它；这说明那道守卫真的在看守。

**相机 RAW 本批没做**：`libraw-wasm@1.6.0` 是 Emscripten **pthreads** 构建（`new Worker(new URL('libraw.js', …), {name:'em-pthread'})` 逐线程），在纯 Node 里 `new LibRaw()` 直接 `Worker is not defined`。要么 renderer 侧跑、要么补 `web-worker` 垫片，都不是"加个依赖"的量级；且本机没有任何真实 RAW 夹具可验。结论：RAW 留在 P1 待排，需要一次"在哪个进程解 + 用谁的 RAW 验"的决策，而不是硬接。

**包体代价（需要后续处理）**：`officeparser` 自身 27 MB，且带进第二份 `pdfjs-dist@6.2.108`（与我们的 6.3.289 并存，目录 34 MB）；`libheif-js` 6.1 MB。仓库现有的 `files` 排除策略（onnxruntime-web 那条注释里记着"漏一条 asar 从 126M 涨到 234M"）说明这个包对体积是敏感项——候选做法：把 PDF 正文从 officeparser 转给自己的 pdfjs（我们本来就有 `PdfRasterizer`），再用 `!node_modules/.pnpm/pdfjs-dist@6.2.108/**` 剪掉重复副本。本批未做，仅记录。

**验证**：新增 `heicConvert.test.ts` 2 条（真 HEIC 夹具入库 `src/main/utils/__tests__/fixtures/halves.heic`，647 B；断言尺寸 + 按行取像素判方向）；`e2e/format-tier.spec.mjs` 加 heic 导入出封面一条。单测 46 文件 / 373 通过 + 1 显式跳过，node typecheck 0 error，`e2e/` 全套 8 条绿。

**公开纠正一条我先前写错的事实**：我在 §七·C 断言「`libheif-js` 1.23.2 会让 `heic-decode` 抛 spread 错误、必须锁版本」。reviewer 反驳后我拆开变量重测：**1.19.8 与 1.23.2 都能正常解码**；那两个报错来自我自己的探针误用 `.all()`（它返回懒解码图片描述数组、没有顶层 width/height）并喂了 ArrayBuffer。归因错了，`pnpm.overrides` 已撤回，代码与注释改成"用默认导出 `one`，不要用 `.all`"。这正是"看着像 A/B 实测、其实两个变量没拆开"的典型。

**确认没问题的（reviewer 提了、我复核后判定不改）**：迁移确实被 `database.ts:142` 逐条包事务 → 018 不会半应用；rebuild 实测 10 万行 ~1.2s，不是启动卡死；`ClipServer` 新接受的扩展名都有通道且没削弱大小/MIME 校验；`ThumbnailService` 的原子写与临时文件清理在新增分支下没有泄漏路径。

**留下未做的（如实列出）**：
- `heicToPngBuffer` 用 `readFileSync` 整块读 + 全分辨率解码（w×h×4 两份），且 `thumb://` 现场重生成**没有并发上限**（只有管线 `PQueue(concurrency:2)` 有）→ Windows 上一批大 HEIC 理论上能压住主进程。它也没有容器内旋转信息（sips 有）。

- 覆盖缺口（同日已补两项）：✅ 新增 `migration018.test.ts`——把库停在 v17、塞进带描述与 OCR 文本的存量行，再单独应用 018，断言老数据仍可搜、`doc_text` 写入后 UPDATE 触发器同步、硬删不留幽灵命中；✅ 新增 `docTextQueue.test.ts`——`DocTextService` 队列语义四条（开关关闭不动作、正常抽取、ENOENT 留 NULL 仍待重试、解析失败落空串认账），为此把仓库面做成可注入参数（默认值不变）。
- 仍未覆盖：打包态（asar / app.asar.unpacked）、Windows 分支、CI 不跑这个 spec（`playwright.config.mjs` + `ci.yml` 本地限定）、`PhotoPreviewVideoFallback` 没点「用系统播放器打开」、64MB 超限分支未测。
